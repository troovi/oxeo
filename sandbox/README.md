# Песочница oxeo

Место для набросков версий библиотеки: как oxeo может работать с частью данных, без полного снимка базы. Здесь думают
над устройством библиотеки и над тем, как ею пользуется приложение, — на маленькой схеме, настоящем сервере и настоящем
клиенте, рядом друг с другом. Песочница — самостоятельный пакет `@oxeo/sandbox`: она стоит на всех библиотеках oxeo и не
принадлежит ни одной из них. Пример у всех версий один, и экран один: каркас и блоки экрана живут в `app/kit` на uikit и
formkit, версия собирает из них свой экран на своей библиотеке.

## Устройство

```
sandbox/
  server/          хост NestJS: монтирует серверный модуль каждой версии под префиксом её ключа (/v-0.1.32/...)
  app/             приложение Vite: стартовая со списком версий, экран версии — по первому сегменту адреса (/v-0.1.32/...)
    kit/           готовые блоки экрана для всех версий (раздел «Экран»)
    styles/        все стили приложения: сброс, тема uikit, токены песочницы, блоки kit
  versions/        версии — пакеты workspace libs, у каждой свой package.json (раздел «Версии»)
    v-0.1.32/      снимок опубликованной библиотеки xeo-scheme 0.1.32 — точка отсчёта
    v-next/        разрабатываемая версия: oxeo 1.0 на локальных пакетах репозитория
    <version>/     устройство любой версии:
      package.json библиотека версии — опубликованные пакеты oxeo, закреплённые точно, или локальные пакеты
      lib/         поверхность библиотеки версии: что версия даёт приложению
      core/        «ядро» приложения на этой библиотеке: схема, домены, параметры операций
      server/      серверный модуль версии: исполнение операций, снимок или его замена, поток событий, посев
      client/      клиент версии: локальные данные и хуки, формы действий, приложение App, экран из блоков kit
      README.md    что версия показывает, что меряет, что в ней замечено
      oxeo-visual.config.ts  каркас карты схемы версии; карта — core/scheme-map.html и .svg
  scripts/         dev.js — сервер и приложение одной командой; visual.js — карты схем версий
```

Правило версии: `core`, `server` и `client` импортируют библиотеку только из своего `lib/`, и по `lib/` видно, чего
версия требует от библиотеки. У `v-next` входы `lib/` повторяют границы пакетов: `lib/scheme.ts` — для `core`,
`lib/server.ts` — для сервера, `lib/client.ts` — для клиента. Версии не импортируют друг друга, чтобы каждую можно было
читать и запускать отдельно. Общее у версий — только `app/kit`.

## Версии

Пример приложения у всех версий один — те же модели схемы, домены, формы действий, страницы App и экран. Версии
различает только библиотека и то, что от неё зависит: поверхность `lib/`, то, как сервер отдаёт данные, и то, как клиент
их держит и читает. Версий два вида.

**Снимок опубликованной библиотеки — `v-<номер>`**, по версии пакета схемы. Его `lib/` реэкспортирует только пакеты из
npm, закреплённые в `package.json` версии. Пример на них не меняется, когда исходники уходят вперёд: снимок нужен, чтобы
видеть и мерить ту библиотеку и сравнивать с ней. Своего кода библиотеки в снимке нет. Сейчас снимок один — `v-0.1.32`,
пакеты прежнего имени, которые ставит CRM: `@companix/xeo-scheme` 0.1.32, `@companix/xeo-toolkit` 0.1.1,
`@companix/xeo-react` 0.1.3.

Пакеты снимка закреплены точными номерами. Имена у них другие, чем у локальных пакетов, поэтому npm кладёт их в корневой
`node_modules` рядом друг с другом, а снимок находит их обычным разрешением модулей.

**Разрабатываемая версия — `v-next`.** Её `lib/` реэкспортирует локальные пакеты репозитория — `core/scheme`,
`core/server`, `drivers/memory`, `core/client`, `core/react` и другие, какие понадобятся. Новая библиотека пишется прямо
в их настоящих папках (`<group>/<package>/lib`), а не в песочнице: то, что проверено в `v-next`, и публикуется, без
переноса кода. В `package.json` версии пакеты oxeo объявлены ссылками `file:` на их папки; разрешение модулей приводит к
ним через ссылки workspace в корне репозитория. Версия берёт сборку пакета (`dist`: ESM — приложению, CommonJS —
серверу), поэтому после правки исходников пакет пересобирается: `npm run build -w=@oxeo/<package>` или все сразу — `npm
run build` в корне репозитория.

Когда новая библиотека опубликована, её можно заморозить снимком: `v-<номер>` — копия `v-next` с пакетами, закреплёнными
номерами из npm. `v-next` после этого идёт дальше. Такой снимок окажется тёзкой локальных пакетов `@oxeo/*`: номер npm
свяжет с workspace, а пред-сборка Vite держит один экземпляр на имя пакета. Снимку понадобятся ссылки на tarball и своё
разрешение модулей.

Версия заводится форком — копией `versions/v-0.1.32` — и меняет только то, чего требует её библиотека. Всё остальное
остаётся как в точке отсчёта и сравнивается с ней один к одному.

1. Скопировать `versions/v-0.1.32` в `versions/<key>` — без `node_modules`.
2. Переименовать пакет в `package.json` версии и задать её библиотеку: у снимка — точные номера опубликованных пакетов,
   у `v-next` — ссылки `file:` на папки пакетов; затем `npm install`. Версия — отдельный пакет: всё, что она импортирует
   (React, роутер, formkit, zod, NestJS), объявлено в её `package.json` теми же диапазонами, что у песочницы, — этого
   ждёт правило `import/no-extraneous-dependencies`, а npm сводит их к общим копиям.
3. Заменить ключ версии там, где он записан в коде: `client/data.ts` (`BASE_URL`), `client/App/index.tsx` (`basename`
   роутера), `client/index.tsx` (`version` экрана), `oxeo-visual.config.ts` (заголовок зоны карты). Имена серверного
   модуля и контроллера (`VersionModule`, `VersionController`) у всех версий одни — хост различает их импортом.
4. Зарегистрировать версию в обоих реестрах: `app/versions.ts` (клиент — название и описание для стартовой) и
   `server/versions.ts` (серверный модуль под префиксом ключа).
5. Переписать README версии: что она показывает, чем её реализация отличается от `v-0.1.32`, что в ней замечено.

## Экран

Экран версии — две половины. Слева дашборд: шапка с именем версии, под ней Domains Operations и Networks. Справа — App:
клиентское приложение версии, как его строил бы настоящий клиент на этой библиотеке. Граница между `app/kit` и версией
проходит по библиотеке: всё, что читает данные приложения и вызывает операции, зависит от библиотеки версии и собирается
версией; kit даёт каркас, view и блоки, которые библиотеки не знают.

| Часть              | Чья                 | Что                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------ | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Каркас             | kit                 | `SandboxScreen` — дашборд (шапка с ключом версии и кнопкой «Сбросить базу» — сброс даёт версия пропом `onReset`, после него страница перезагружается; плашка `ResyncBanner`; колонки `domains`, `network`) и половина `app`, окна и тосты kit; `SandboxScreen.Message` — экран одного состояния (подключение)                                                                                                                                                                                                                                                                      |
| Domains Operations | kit по карте версии | `DomainsPanel` по карте `DomainGroup[]`: домены группами, в группе — действия с именем метода и хуком формы. Кнопка действия открывает окно kit; форму пишет версия сама (`client/forms`: хук `use<Name>Form` на действие, formkit на полях kit) и в отправке вызывает операцию через `run` — успех закрывает окно с тостом, отказ — тост                                                                                                                                                                                                                                          |
| Networks           | kit                 | `NetworkPanel` — все обмены с сервером вместо вкладки Network браузера: запросы (метод, адрес, заголовки, параметры, статус, ответ, вес, время) и сообщения потока. Версия ходит на сервер через `network.fetch` и `network.stream`; подпись строки по своему протоколу даёт пропом `summary`                                                                                                                                                                                                                                                                                      |
| App                | версия из view kit  | приложение версии на `react-router` (`client/App/` у `v-0.1.32`): роутер с `basename` — префиксом версии, страницы — файлами папки. Корень (`/v-0.1.32`) — главная, раздел — полный список (`/v-0.1.32/workers`), сегмент списка — свой маршрут (`/v-0.1.32/shifts/recruiting`), запись — `/v-0.1.32/workers/12`. View kit — `AppFrame` (строка разделов), `AppPage` с частями `Section`, `Empty` и `Segments` (сегменты-маршруты над `Segments` uikit), `SectionTiles`, `RecordFields` (поля-ссылки ведут в связанные записи), `RecordsTable` (все записи, строка ведёт в запись) |

Окна kit — реестр uikit `createPopupRegistry` (`kit/popups.ts`), формы — `@companix/formkit` с полями над контролами
uikit (`kit/formkit/`: примитивы и раскладки, как пакет `formkit` CRM). Итог операции — тост uikit (`kit/toaster.tsx`):
успех закрывает окно, отказ оставляет его открытым. JSON в Networks — деревом `react-json-view-lite` со своими классами
подсветки: узлы сворачиваются, глубже второго уровня свёрнуто сразу. Стили — по владельцам в `app/styles/components`,
только SCSS с токенами темы (`app/styles/tokens.scss`, светлая тема), без Tailwind — как в CRM-клиенте.

## Запуск

Один раз — зависимости и сборка в корне репозитория: `npm install`, `npm run build`. Затем:

```
npm run dev -w=@oxeo/sandbox        # сервер :4500 и приложение :4501 вместе
npm run server -w=@oxeo/sandbox     # только сервер (tsx watch)
npm run app -w=@oxeo/sandbox        # только приложение (vite)
npm run visual -w=@oxeo/sandbox     # карты схем всех версий; одна — `-- <version>`
npm run typecheck -w=@oxeo/sandbox  # типы всей песочницы вместе с версиями
npm run build                       # все пакеты oxeo в нужном порядке — после правки библиотеки
```

Приложение — http://localhost:4501, версии — http://localhost:4501/v-0.1.32 и http://localhost:4501/v-next. Запросы
`/api/<version>/...` приложение проксирует на сервер, так что адрес сервера клиент не знает. Второе окно браузера —
второй клиент: по нему видно, как реплики узнают о чужих изменениях. Сервер засевается заново при каждом перезапуске и
по кнопке «Сбросить базу» в шапке — открытые страницы видят новую эпоху: `v-0.1.32` просит перезагрузку, `v-next`
забывает всё и перезапрашивает своё. Пересборка пакета роняет `tsx watch` сервера (`rm -rf dist` посреди перезапуска) —
он поднимется со следующей правкой файла сервера.

## Как устроено окружение

- **Библиотека — у версии.** Пакеты версия берёт из своего `package.json` обычным разрешением модулей — у `tsc`, `tsx` и
  Vite нет ни алиасов, ни `paths` на библиотеку. У снимка это закреплённые копии из npm, у `v-next` — локальные пакеты
  репозитория, то есть их сборки. Имена у них разные, поэтому экземпляр схемы (хранилище метаданных моделей — модульный
  синглтон) у каждой версии свой и единственный. Классы ошибок библиотеки — тоже экземпляр версии, поэтому отказы домена
  и целостности ловит фильтр версии (`server/domain-exceptions.filter.ts`), а у хоста — общий фильтр HTTP-исключений и
  500.
- **uikit и formkit — из npm**, как у CRM-клиента: код — сборки пакетов, стили — `@companix/uikit/dist`. Тема uikit своя
  (`app/styles/theme`, копия темы `classic`): в npm публикуется только `dist`, а токены копятся в карте модуля
  `@companix/uikit/dist/theme.scss`, поэтому тема подключается к нему.
- **Сервер без базы.** База сервера — in-memory драйвер oxeo, как у клиента 0.1; при старте сервер засевается операциями
  доменов (детерминированно, та же база на каждый запуск). Песочница думает о протоколе между приложением и библиотекой,
  не о хранилище; когда вопрос дойдёт до запросов к Mongo, версия подключит `@oxeo/server` в своём серверном модуле.
- **Карты схем — `@oxeo/visual`** через его API `buildSchemeMap` под `tsx` (`scripts/visual-build.ts`): схема версии
  грузится на её библиотеке, как на сервере; CLI `oxeo-visual` грузит TypeScript-конфиг через `ts-node`, которого в libs
  нет. Конфиг версии — в формате инструмента (`oxeo-visual.config.ts`, пути — от его папки); каждая версия собирается в
  своём процессе — декораторы двух схем в одном процессе задвоили бы хранилище метаданных.
- **Сервер на `tsx`.** esbuild не пишет метаданные декораторов, поэтому зависимости в конструкторах NestJS указываются
  явно — `@Inject(Service)`.
- `tsconfig.json` подключает глобальные типы `multer`: типы `utils-browser`, которые берёт uikit, тянут `@oxeo/types` с
  `Express.Multer`.
- Стиль кода — `code-style` автора; устройство клиента — по образцу `ARCH.md` CRM-клиента (view и controller, окна через
  реестр, формы formkit, стили по владельцам); документы и комментарии — по-русски.
