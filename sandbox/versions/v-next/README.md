# v-next — oxeo 1.0, сервер первым

Разрабатываемая версия библиотеки на локальных пакетах репозитория: `core/scheme`, `core/server`, `drivers/memory`,
`core/client`, `core/react` подключены ссылками `file:` в `package.json` версии, и библиотека пишется прямо в их папках
(README песочницы, «Версии»). Папки версии повторяют структуру проекта на oxeo (README репозитория): `core` — общее
ядро, `server` — приложение, которое его исполняет, `client` — приложение, которому от ядра нужны только типы.
Устройство — набросок `ideas/sketch-1`: операцию исполняет только сервер, клиент не повторяет домены, а держит живую
часть базы — то, что прочитали страницы, — и получает изменения готовыми. Пример тот же, что у `v-0.1.32`: те же схема,
домены, формы действий, страницы App и экран; отличаются библиотека, протокол и то, как клиент читает данные.

## Что внутри

**Схема и домены** (`core/`) — как у `v-0.1.32`. Библиотеку ядро берёт из `lib/scheme.ts`, то есть из `@oxeo/scheme`:
там и схема, и контракт доменов, и `schemaOf`. Это исполняет сервер; клиент импортирует из `core` только типы и
перечисления `keys.ts`, поэтому в его сборку не попадают ни модели, ни домены, ни zod.

**Сервер** (`server/`) — `createServerShell` над in-memory базой: очередь вызовов, контекст, ревизии. Событие журнала
несёт, кроме вызова и результата, новые версии всех записей, которые тронула операция (`changes`; `record: null` —
удалена); счётчики номеров клиентам не уходят. Снимка нет. Маршруты под `/v-next`:

- `POST domains/<domain>/<method>` — вызов, ответ — событие (актор — заголовок `x-worker-id`, без него — система);
- `POST data/query` — пакет запросов `{ queries }`: `get` по id, `find` по фильтру с операторами (`where: null` —
  коллекция целиком), `count`. Идёт мимо очереди вызовов; ответ — записи с захватом по ссылкам на один уровень
  (`ReferenceTo`, `ReferenceSet`, `BelongsTo`) и результат каждого запроса;
- `GET events` — поток событий SSE, `GET stats` — сводка, `POST reset` — сброс базы с посевом заново; после посева
  подключённым клиентам — `resync`.

**Клиент** (`client/`) — `createClient<AppScheme, AppDomains>` из `core/client`: схема и домены только типами. Старт —
только поток событий; пока он не открыт, приложение не рисуется. Дальше страницы сами догружают то, что читают.

- Страницы App — компоненты в `observer` (`@oxeo/react`), данные читаются прямыми вызовами `data.<collection>.get/find/
  all/count`. Проход тела собирает всё, чего не хватило, в один пакет; пока он идёт — заглушка `AppPage.Loading`, отказ
  после повторов — `AppPage.Failed` с повтором. Страница записи с её связями — одно обращение к серверу.
- Главная — `count` по разделам: числа считает сервер, записи не загружаются.
- `ShiftsPage` — все смены и сегменты стадий: сегмент — живой запрос `find({ stage })`. Событие несёт смену целиком, и
  клиент сам решает, вошла она в сегмент или вышла, даже если до операции смены у него не было.
- Поля выбора записей в формах — мост `useData` (`forms/shortcuts/entities.shortcuts.ts`): варианты читает поле formkit,
  а не компонент в обёртке; загрузку поле показывает по `isLoading`. Значения справочника — запрос по словарю, а не все
  значения.
- Пересинхронизация мягкая: команда сервера, смена эпохи, разрыв ревизий или переподключение потока — клиент забывает
  всё, смонтированные страницы перезапрашивают своё; перезагрузки нет. Обрыв потока — плашка «Нет связи».
- Networks — пакеты запросов подписаны их запросами, события — ревизией, методом и числом записей.

## Что меряется

Networks показывает каждый пакет запросов с весом и временем: сколько данных нужно странице, а не всей базе. Сводка
сервера — `GET /v-next/stats`: записи по коллекциям и вес всей базы в байтах JSON — столько в `v-0.1.32` весил снимок
при входе. На посеве по умолчанию база — около 266 КБ; запись сотрудника приходит одним пакетом около 1 КБ, главная —
около 130 байт, запись смены с участниками и их сотрудниками — около 5 КБ.

## Замечено при сборке

- `tsx watch` сервера падает, когда пакет пересобирается (`rm -rf dist`), и ждёт следующей правки файла сервера.
- Склейка ответа на пакет с потоком событий — известная проблема первой версии (набросок, «Отрезано»): ответ кладётся
  как есть, в каком бы порядке он ни пришёл относительно событий.
