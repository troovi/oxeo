# Набросок 1 — oxeo 1.0: сервер первым, клиент держит живую часть базы

Набросок следующей версии oxeo, при которой приложение работает без полного снимка базы. Устройство описано по принятым
решениям и дополняется по мере обсуждения. Воплощён в `versions/v-next`: библиотека — в локальных пакетах oxeo, их
раскладка и структура проекта на oxeo — README репозитория; `.ts` наброска остаются следом мысли, рабочий код — там.

| Файл          | Что показывает                                                                                                          |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `protocol.ts` | фильтр с операторами, запросы и их пакет, ответ, событие журнала с новыми версиями записей, сообщения потока            |
| `matcher.ts`  | сверка записи с фильтром — один код для in-memory драйвера и клиента, семантика Mongo                                   |
| `server.ts`   | сборка журнала в версии песочницы; оболочка: событие с версиями тронутых записей, пакет запросов с захватом ссылок      |
| `client.ts`   | ядро клиента без React: хранилище версий, покрытие, чтения и сборщик прохода, пакеты с повторами, события, `DomainsAPI` |
| `react.tsx`   | обёртка `observer`: проход тела, свои границы Suspense и ошибок, умолчания `fallback` и `error`; мост `useData`         |
| `app.tsx`     | страницы песочницы на 1.0: сборка клиента, главная со счётчиками, запись сотрудника, смены месяца, форма, обработчик    |

## Принцип

Операцию исполняет только сервер: домен работает над полной базой, там же проверяется целостность схемы. Клиент операции
не повторяет. Он держит живую часть базы — то, что прочитали его экраны, — и получает изменения готовыми.

Версия 0.1 (релиз `xeo-v0.1.32`) повторяла каждую операцию на клиенте. Пользы повтор не давал: клиент всегда исполнял
операцию после сервера, который уже проверил и записал её. Зато повтор требовал полной копии базы у каждого клиента и
строгого детерминизма доменов.

## Домен

Домен исполняется только на сервере, поэтому контекст вызова больше не запись для повтора. Что домену дают, делится по
тому, меняется ли это от вызова к вызову.

- **Окружение** — одно на все вызовы: `collections` и выдача идентификаторов `ids`. Приходит в конструктор, домен читает
  `this.ids`.
- **Контекст** — свой у каждого вызова: `actor` — кто вызвал, `at` — единый момент вызова, его задаёт посев истории,
  `today` — дата в поясе приложения. Приходит вторым аргументом метода, он же уходит в событие: его читают подписчики на
  сервере. Метод, которому контекст не нужен, его не объявляет.

Домены исполняет `DomainRuntime`: очередь вызовов, контекст, ревизии, рассылка событий и ответы на пакеты запросов. До
реализации он назывался журналом, но событий не хранит, поэтому в `.ts` наброска имя прежнее.

Параметры вызова проверяет рантайм, а не приложение. Проект передаёт ему реестр схем `appParams`, собранный
`createDomainsParams<AppDomains>`: по типу доменов компилятор требует схему на каждый публичный метод. `run` проверяет
каждый вызов, в том числе посев, ещё до очереди. Операции нет в реестре — `notFound`, параметры не прошли — `ParamsError`.
В домен и событие идёт разобранное значение. Реестр заодно перечисляет публичные операции: TS-`private` в рантайме не
виден, поэтому вызов без схемы — неизвестная операция.

## Событие

Сервер рассылает событие всем клиентам и не знает, кто что держит. В событии:

- `domain`, `method`, `params`, `result`, `ctx.at` — для подписчиков на сервере и вызывающего;
- новые версии всех записей, которые затронула операция, — целиком; `null` — запись удалена.

Патчей и строк таблиц связей в событии нет. Применение идемпотентно: клиент кладёт новую версию записи на место прежней.

Порядок задаёт только поток: его события идут подряд, и ревизия клиента растёт только на них. Другая эпоха или разрыв
ревизий значат, что события потеряны, — это пересинхронизация. Очереди событий на клиенте нет: применение синхронно,
ждать нечего.

Ответ собственного вызова — второй канал, поэтому событие из него применяется сразу, только если поток до него ещё не
дошёл. Иначе его версии могут быть старше тех, что принёс поток. Ревизию такое применение не двигает: поток доставит то
же событие сам. Если ответ обогнал поток и более раннее чужое событие тронуло ту же запись, она на миг вернётся назад, а
следующее событие потока её исправит.

Если операция упала после первой записи, сервер, как в 0.1, рассылает команду пересинхронизации. Теперь она дешёвая:
клиент забывает запросы, а смонтированные компоненты перезапрашивают то, что читают, без перезагрузки страницы.

Версии записей неизменяемы: новая версия — новый объект, старый объект не меняется никогда. Кто прочитал запись, держит
её версию на момент чтения. Какие поля изменились, клиент узнаёт сравнением старой и новой версии — по ним обёртка
решает, кого перерисовать.

## Запросы

Клиент держит результаты запросов. Запрос задаётся одним из трёх способов:

- запись по id;
- коллекция и фильтр: равенство и операторы `gte`, `gt`, `lte`, `lt`, `in`, `ne`;
- коллекция целиком.

Сервер выполняет запрос через коллекции oxeo над базой. Клиент тем же фильтром сверяет записи, пришедшие в событиях:
запись, которая стала подходящей, входит в результат, переставшая подходить — выходит.

Пакет запросов идёт мимо очереди вызовов: ждать операции ему незачем, ревизии в ответе нет. Поэтому чтение может застать
операцию на середине, а итоговые версии принесёт её событие.

Фильтр с операторами — это `findBy` коллекций oxeo. Mongo-драйвер переводит его в запрос базы. In-memory драйвер (сервер
песочницы, тесты доменов) и клиент сверяют записи одним и тем же кодом. Домены получают операторы тоже: широкая операция
может читать смены периода, а не всю коллекцию.

Записи из события собственного вызова клиент сохраняет, даже если их не ждёт ни один запрос: после `create` обычно
открывают созданное.

К каждой отданной записи сервер добавляет записи, на которые ведут её поля-ссылки (`ReferenceTo`, `ReferenceSet`,
`BelongsTo`), на один уровень. `HasMany` не захватывается.

Счётчик — `data.<collection>.count(where)` с тем же фильтром. Если коллекция загружена целиком, число считается на
месте. Иначе его считает сервер, а клиент перезапрашивает число с небольшой задержкой, когда в событиях приходят записи
этой коллекции. Несколько событий подряд дают один перезапрос. Других агрегатов в oxeo нет.

Загруженный запрос живёт до конца сеанса. Клиент и так получает все события, поэтому держать запрос полным стоит только
сверки на клиенте. Покрытие: коллекция целиком покрывает любой запрос к ней, запись по id покрыта, если она уже есть у
клиента. Пересинхронизация — забыть всё: смонтированные компоненты перезапросят то, что читают, а ответ пакета, ушедшего
до неё, не кладётся.

## Экран

Компонент, который читает данные, оборачивается в `observer`. Данные читаются не хуками, а прямыми вызовами объекта
данных, как в MobX: `data.<collection>.get(id)`, `.find(where)`, `.all()`.

Обёртка вызывает тело компонента и отслеживает каждое чтение за проход рендера — в теле, в цикле, в условии, внутри
вызванной функции. Чтение, которому не хватило данных, не останавливает рендер: оно записывает потребность и отдаёт
пустое значение того же вида — `null` или `[]`. Если после прохода остались потребности, обёртка отправляет их одним
пакетом запросов, а пока ответа нет, рисует свою заглушку. Потребности всех компонентов одного такта уходят одним
пакетом, одинаковые `get` одной коллекции склеиваются в один список id.

Подписка одна на компонент — по всему прочитанному, включая поля записей. Код компонента о загрузке не знает, и `null`
значит «записи нет».

```tsx
const ParticipantRow = observer(
  ({ shiftId }: { shiftId: number }) => {
    return <Row shift={data.shift.get(shiftId)} />
  },
  { fallback: <Row.Loading /> }
)

export const WorkerPage = observer(
  () => {
    const worker = data.worker.get(workerId)
    const participants = data.participant.find({ workerId })

    return participants.map((participant) => (
      <ParticipantRow key={participant.participantId} shiftId={participant.shiftId} />
    ))
  },
  { fallback: <AppPage.Loading /> }
)
```

Обёртка не отличает первую загрузку от обновления: любой проход, которому не хватило данных, прячет всё её тело за
заглушкой до ответа. Событие приносит только изменённые записи. Если оно добавило в живой `find` строку, а записи по её
ссылке у клиента нет, один новый ряд спрячет весь список. Поэтому обёртка — ещё и граница заглушки: чтение, из-за
которого страница не должна пропадать, выносится в свой компонент со своей обёрткой, как строка выше. Заглушка встанет
только на его месте. Где делить экран, решает приложение: библиотека такое чтение не находит и не предупреждает. Цена
деления: у каждой обёртки свои границы Suspense и ошибок, а заглушке нужен размер того, что она заменяет.

Смена фильтра внутри обёртки тоже даёт заглушку, если новый запрос не покрыт. Прежний вид до ответа держат средства
React: `startTransition` или `useDeferredValue`. После `resync` заглушку показывают все обёртки: клиент забыл всё.

Риск — забытая обёртка: компонент без `observer` покажет то, что есть у клиента, но не загрузит недостающее и не
обновится.

Исключение — код, который вызывают чужие компоненты: `useOptions` поля formkit, колбэки списков uikit. Хозяин такого
кода не в обёртке, и оборачивать его нельзя — общие пакеты интерфейса не знают oxeo. Для этого есть мост, хук
`useData(fn)`. Он выполняет функцию со своим сборщиком в компоненте-хозяине, подписывает хозяина на прочитанное и
догружает недостающее после рендера. Заглушку рисовать негде, поэтому вместо неё мост отдаёт `isLoading` — договор
formkit его и ждёт.

```ts
const useWorkerOptions = () => {
  const { value: workers, isLoading } = useData(() => data.worker.all())
  const options = workers.map((worker) => ({ value: worker.workerId, title: worker.name }))

  return { options, isLoading }
}
```

У обёртки три состояния: загружается — `fallback`, готово — тело, не удалось — `error`. Умолчания обоих видов задаются
один раз — при сборке обёртки над клиентом (`createObserver`), а каждая обёртка переопределяет их там, где нужен свой
вид. Границы Suspense и ошибок у обёртки свои, внутри, и приложению их расставлять не нужно. Неудавшийся пакет обёртка
сначала повторяет сама, несколько раз с растущей паузой, всё это время показывая `fallback`. Только потом она показывает
`error`, где `retry` отправляет запросы заново. Ответ сервера «записи нет» ошибкой не считается: это `null`. Ошибку
доступа (истёкшая сессия) ловит слой HTTP приложения, а не обёртка.

```tsx
const client = createClient<AppScheme, AppDomains>({ transport })

const observer = createObserver(client, {
  fallback: <Spinner />,
  error: ({ retry }) => <ErrorState onRetry={retry} />
})

export const WorkerPage = observer(Body, { fallback: <AppPage.Loading /> })
```

## Вне рендера

В обработчике, отправке формы и эффекте обёртки нет: чтение не отслеживается и не загружает недостающее.

- **Своя версия формы** — запись, прочитанная при открытии: объект версии не меняется. Копия не нужна.

  ```tsx
  const [request] = useState(() => data.request.get(requestId)) // версия на момент открытия
  ```

- **Синхронное чтение** — `data.<collection>.get/find/all` — отдаёт только то, что у клиента покрыто: коллекция
  загружена целиком, запрос с этим фильтром живёт, запись с этим id есть или сервер ответил, что её нет. Непокрытое
  чтение не отдаёт неполный ответ, а бросает ошибку с подсказкой: прочитать при рисовании или загрузить явно.
- **Явная загрузка** — для обработчика, которому нужно то, чего экран не читал. Непокрытое идёт на сервер, ответ
  становится живым запросом сеанса; покрытое отвечается сразу.

  ```ts
  const payouts = await data.salaryPayout.load()
  const options = await data.option.load({ dictionary: 'regions' })
  ```

## Клиент без схемы в рантайме

Клиенту схема нужна только типами: по ним `data.<collection>` знает тип записей. Выдача и события несут записи вместе с
коллекцией и id, фильтр сверяется по полям самой записи, ссылки захватывает сервер. Декораторы, `DataScheme`,
`DataProcessor` и таблицы связей нужны только серверу и тестам доменов.

Раскладка пакетов держит это правило: `core` пишется на `@oxeo/scheme`, сервер исполняет его через `@oxeo/server` и
драйвер, клиент получает из `core` только типы и работает на `@oxeo/client`. Из `@oxeo/scheme` в рантайм клиента
попадает лишь сверка `matches`: сборка `@oxeo/client` вшивает вход `@oxeo/scheme/filter`, потому что один и тот же код
нужен клиенту и драйверу памяти. В production-сборке `v-next` нет ни одного модуля zod, `@oxeo/scheme`, `core/scheme` и
`core/domains`.

## Отрезано

- Постраничность, сортировка с лимитом и агрегаты, кроме счётчика.
- Ограничение памяти: долгий сеанс копит открытое, в худшем случае — вся база, как в 0.1.
- Видимость данных: каждый клиент получает все изменения всех.
- Склейка выдачи с потоком событий — известная проблема первой версии. Ответ на запрос (HTTP) и события (поток) могут
  прийти в любом порядке. Если событие обогнало ответ, клиент положит версию записи до события, и устаревшее держится,
  пока запись снова не изменят. Если ответ обогнал события, клиент на миг откатится к старым версиям и сойдётся сам.

## На будущее

- **Политика забывания, которую задаёт приложение.** Сейчас запрос живёт до конца сеанса. Будущая версия может дать
  приложению выбор: забывать запрос без подписчиков сразу, через время (как `gcTime` в React Query) или по объёму
  памяти. Для этого понадобится учёт, какой запрос держит какую запись, включая записи, захваченные по ссылкам.
- **Склейка выдачи с потоком событий.** Четыре пути исправить проблему первой версии. Ревизии в ответе на пакет сейчас
  нет, и путям, которые на неё опираются, её придётся вернуть:
  - ждать и доигрывать: ответ кладётся, когда клиент дошёл до его ревизии; если клиент ушёл дальше, к загруженному
    заново применяются события после ревизии ответа из короткого журнала последних событий;
  - метки ревизий у записей: версия кладётся, только если она новее; удаления помнятся «надгробиями»;
  - один упорядоченный канал: сервер отдаёт ответ в поток событий клиента прямо в очереди вызовов, и порядок держит сам
    канал;
  - доигрывать на клиенте: клиент и так получает все события, поэтому хранит их, пока пакет в полёте, и применяет поверх
    ответа те, что новее его ревизии.
- **Рассылка частичной записи.** Вместо пересинхронизации сервер может разослать событие с тем, что успело записаться,
  вместе с ошибкой. Тогда реплики остаются согласованными с базой без повторной загрузки.
